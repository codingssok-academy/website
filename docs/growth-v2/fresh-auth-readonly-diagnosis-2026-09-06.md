# 시험 DB 인증 오류 읽기 전용 진단

기록일: 2026-09-06 (한국 시간)

최종 정리 상태: 같은 날 16:19 KST 확인 기준으로 대상 재검증 후 가짜 자료 정리와 0건 검사가 완료됐다. [정리 완료 기록](fresh-manual-fixture-cleanup-2026-09-06.md) 참고. 아래의 인증 진단 당시 기록은 그대로 보존하며, 인증 오류의 근본 원인은 여전히 미확정이다.

후속 상태: 같은 날 16:12 KST에 진도 2건이 이번 가짜 학생·관리자 계정 소유이며 초기값과 일치함을 확인했다. 아래는 인증 진단 당시의 기록이고, 소유자 확인 결과는 [진도 2건 확인 기록](fresh-fake-progress-ownership-2026-09-06.md)을 따른다. 삭제는 아직 실행하지 않았다.

## 결론

기존 키와 기존 DB 설정을 그대로 사용한 읽기 요청 **19건 모두 성공**했다. 앞서 실패했던 학생 및 선생님 배정 테이블도 정상 응답했다. 그러나 이전 오류의 상세 원인을 확정하거나 재발이 없다고 보장한 것은 아니다. **정리 도구의 Bearer 헤더를 제거한 것이 근본 해결책이었다는 결론은 유보한다.** 기본 SDK 방식도 이번에는 성공했다.

이번 단계는 인증 진단만 수행했다. 가짜 계정·학생·파일·진도 자료는 삭제하지 않았다. 홈페이지 소스, DB 구조·권한, 프로젝트 키와 환경변수를 변경하지 않았다. 운영 DB 연결, push, PR, 배포는 하지 않았다.

## 대상 및 진단 안전장치

- 유일한 대상: `codingssok-growth-v2-fresh-test` (`opcdcuedhwyuyhzaubpu`).
- Dashboard에서 프로젝트 이름과 ref를 확인하고 기존 Secret key 복사 버튼만 사용했다. 키 생성·교체·폐기는 하지 않았다.
- 저장소 밖의 일회성 진단 도구를 사용했다. 기존 정리 도구는 수정하거나 실행하지 않았다.
- 허용한 요청은 13개 테이블의 `GET`, `select=*&limit=0`뿐이다. 자료 본문은 받지 않고 응답 상태·수량·오류 정보만 확인했다.
- 정확한 시험 호스트, 테이블 목록, GET 방식, 본문 없음, limit 0, 쿼리 매개변수 2개, 최대 요청 19회를 코드로 제한했다. 리디렉션을 금지하고 요청별 15초 제한을 뒀다.
- 사용자 로그인·토큰 발급·RPC·저장소 파일 접근·DB 쓰기 경로는 포함하지 않았다.
- 실제 키·JWT는 로그에서 가리도록 했으며, 키 값은 화면에 출력하거나 파일에 저장하지 않았다. 복사 직후 클립보드를 비우고 프로세스 종료 시 임시 환경변수를 제거했다.
- 새 패키지를 설치하지 않았다. 설치돼 있던 `@supabase/supabase-js` 버전은 `2.110.0`이다.

## 이전 실패 기록 확인

[시험 프로젝트 API Gateway 로그](https://supabase.com/dashboard/project/opcdcuedhwyuyhzaubpu/logs/edge-logs)에서 최근 한 시간의 400번대 요청을 필터링했다.

- 15:51:50 KST: `GET /rest/v1/teacher_student_assignments?select=*&limit=0`, HTTP 401.
- 로그 ID: `4bb35bcd-c257-4cd9-b863-7949a2fe2552`.
- User-Agent: `node`. 브라우저로 Secret key를 보내서 생긴 차단이라고 볼 근거는 없다.
- 표시된 게이트웨이 오류 헤더 `x_sb_error_code`: null.
- Details와 Raw 모두 확인했으나, 표시된 로그에는 JWT 검증 실패의 구체적인 문구·만료 시각·응답 본문이 없었다.
- 15:44:33 `user_progress` 요청 및 15:40:10 학생 HEAD 요청의 401 기록도 있었다. 401이라는 상태만으로 각각의 세부 원인을 동일하다고 단정하지 않는다. 중간의 공개 키·익명 접근 검사는 예상된 권한 거절일 수 있으므로 모두 같은 장애로 세지 않는다.
- [PostgREST 로그](https://supabase.com/dashboard/project/opcdcuedhwyuyhzaubpu/logs/postgrest-logs)의 최근 한 시간은 `No results found`였다. 로그 미표시가 이전 오류가 없었다는 증거는 아니다.

[공식 오류 코드 문서](https://supabase.com/docs/guides/api/rest/postgrest-error-codes)는 `PGRST303`을 JWT claims 검증·해석 실패로 구분한다. 단순 테이블 권한 부족과는 다른 분류이며, 어떤 JWT 검증 항목이 실패했는지까지는 이 코드만으로 알 수 없다. [공식 API 키 문서](https://supabase.com/docs/guides/getting-started/api-keys)는 새 키를 `apikey`에 전달하도록 안내하지만, 이번 기본 SDK 요청도 성공했으므로 문서의 일반 설명을 과거 장애의 직접 증거로 대체하지 않는다.

## 남은 확인 및 다음 경계

1. 현재 읽기 접근은 성공했다. 간헐적 인증 실패의 근본 원인은 미확정이다. 오류를 재현하려고 반복 요청하거나 키·권한·인증 구조를 임의로 바꾸지 않는다.
2. 재발 시 새 진단 도구가 남기는 구체적 오류 문구, 요청 ID, 시각을 확보해 원인을 좁힌다. 필요하면 이 기록을 사용해 Supabase 지원에 문의할 수 있지만, 이번에는 문의를 제출하지 않았다.
3. 가짜 자료 정리 전에는 Auth 계정·학생·두 파일과 진도 2건의 동일 실행 소유 여부를 모두 다시 확인해야 한다. 그 검사가 성공하기 전까지 삭제하지 않는다.

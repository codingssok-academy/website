# Growth 2.0 테스트 백엔드 검증 계획

> 아직 실행하지 않은 계획입니다. 실제 검증은 독립 로컬 Supabase를 만든 다음 단계에서 진행합니다.

## 1. 검증 환경 원칙

- 운영 Supabase와 운영 DB를 사용하지 않음
- `localhost` 또는 `127.0.0.1`의 독립 로컬 Supabase만 사용
- migration은 Growth 2.0 전용 `0001`부터 적용
- 가상 Auth 계정만 생성
- 실제 이름, 이메일, 전화번호를 사용하지 않음
- 각 테스트는 스스로 데이터를 준비하고 정리
- 테스트 순서에 의존하지 않음
- 성공 사례와 차단 사례를 모두 확인
- 브라우저용 키로 `service_role`을 사용하지 않음

## 2. 가상 계정 구성

| 계정 | 역할 | 연결 |
|---|---|---|
| `student-a@example.invalid` | 학생 A | 학부모 A, 선생님 A와 연결 |
| `student-b@example.invalid` | 학생 B | 학부모 B, 선생님 B와 연결 |
| `parent-a@example.invalid` | 학부모 A | 학생 A만 연결 |
| `parent-b@example.invalid` | 학부모 B | 학생 B만 연결 |
| `teacher-a@example.invalid` | 선생님 A | 학생 A만 담당 |
| `teacher-b@example.invalid` | 선생님 B | 학생 B만 담당 |
| `admin@example.invalid` | 관리자 | 전체 관리 |
| `inactive-parent@example.invalid` | 비활성 학부모 | 과거에 학생 A와 연결됐으나 해제 |

`example.invalid`는 실제 메일 발송에 쓰이지 않는 예약 도메인입니다. 실제 운영 계정과 섞이지 않습니다.

## 3. migration과 구조 검증

1. 완전히 빈 독립 로컬 Supabase에 `0001` 적용
2. 모든 표, 인덱스, 제약, 트리거, RLS 정책 생성 확인
3. migration 전체 롤백이 아니라 로컬 DB 재생성으로 처음부터 재검증
4. 활성 migration에 기존 운영 migration이 섞이지 않았는지 확인
5. 모든 주요 ID가 UUID인지 확인
6. 모든 주요 표에 작성·수정 시각과 작성·수정자가 있는지 확인
7. `private` 스키마가 Data API 노출 목록에 없는지 확인
8. `SECURITY DEFINER` 함수의 `search_path`가 빈 값으로 고정됐는지 확인
9. `anon`에 Growth 표 권한이 없는지 확인
10. 공개 함수 실행 권한이 `authenticated`, `service_role`로 제한됐는지 확인

## 4. 학생 권한 테스트

### 허용

- 학생 A가 자신의 학생 행 조회
- 자신의 미션과 완료 상태 조회
- 자신의 XP 거래 내역 조회
- 자신의 활동 이벤트 조회
- 자신의 획득 배지 조회
- 자신의 공개 평가 조회
- 공개 평가의 잘한 점과 다음 목표가 학생 홈 응답에 포함

### 차단

- 학생 A가 학생 B의 학생 행 조회
- 학생 B의 XP·미션·이벤트·배지 조회
- 자신의 XP INSERT·UPDATE·DELETE
- 자신의 미션 완료 행 직접 UPDATE
- 선생님 평가 INSERT·UPDATE
- `draft` 또는 `archived` 평가 조회
- 타 학생 프로젝트 조회

## 5. 학부모 권한 테스트

### 허용

- 학부모 A가 학생 A 목록 조회
- 학생 A의 공개 주간 평가 조회
- 학생 A의 공개 프로젝트·이벤트 조회

### 차단

- 학부모 A가 학생 B 조회
- 연결이 비활성인 학부모가 학생 A 조회
- 종료일이 지난 연결로 자녀 조회
- 자녀 평가·XP·미션·프로젝트 직접 수정
- 자녀의 `draft` 평가 조회

## 6. 선생님 권한 테스트

### 허용

- 선생님 A가 담당 학생 A 조회
- 학생 A의 평가 초안 생성
- 학생 A의 초안 수정
- 초안 개념 추가·수정·제거
- 학생 A 프로젝트와 프로젝트 초안 작성
- 유효한 초안을 공개 절차로 공개

### 차단

- 선생님 A가 미담당 학생 B 조회
- 학생 B 평가 초안 생성·수정
- 요청에 선생님 B의 ID를 넣어 담당 관계 우회
- 공개 평가의 문장 직접 덮어쓰기
- 학생 XP 직접 INSERT
- 비활성 담당 관계로 학생 A 접근

## 7. 관리자 권한 테스트

- 전체 학생·사용자·연결 관계 조회
- 학부모 연결 생성·비활성
- 선생님 담당 관계 생성·비활성
- 미션·배지 정의 생성·비활성
- 전체 평가 상태와 버전 조회
- 요청 본문에 `role=admin`만 넣은 일반 계정은 관리자 권한을 얻지 못함
- 사용자 수정 가능한 메타데이터를 `admin`으로 바꿔도 권한을 얻지 못함

## 8. 초안과 공개 테스트

1. 학생 A의 주간 평가를 `draft`로 생성
2. 학생 A와 학부모 A에게 보이지 않는지 확인
3. 담당 선생님 A에게만 보이는지 확인
4. 필수 퍼센트 스냅샷이 없으면 공개 실패
5. 정상 공개 후 학생 A와 학부모 A에게 보임
6. 학생 B와 학부모 B에게 보이지 않음
7. 공개본 문장 직접 UPDATE 실패
8. 버전 2 초안을 생성하고 수정
9. 버전 2 공개 후 버전 1이 `archived`인지 확인
10. 학생·학부모에게 현재 공개 버전 하나만 보이는지 확인

## 9. XP 중복 방지 테스트

- 동일 학생 + 동일 `idempotency_key` 두 번째 INSERT 실패
- 동일 학생 + 동일 원인 유형·원인 ID·사유 두 번째 INSERT 실패
- `idempotency_key` NULL 실패
- `source_id` NULL 실패
- XP 0 실패
- 음수 XP 실패
- 같은 학생의 서로 다른 정상 이벤트는 각각 성공
- 서로 다른 학생은 독립된 정상 이벤트를 가질 수 있음
- 학생·학부모·선생님 직접 INSERT 실패
- 안전한 서버 작업만 INSERT 성공

초기 MVP에서는 XP 차감과 음수 보정을 지원하지 않습니다. 운영 보정 규칙이 정해지면 별도 테스트 계획을 추가합니다.

## 10. 미션 중복 완료 테스트

- 같은 학생·미션·배정키 중복 배정 실패
- 완료 상태에는 완료 시각과 완료 고유키가 반드시 필요
- 같은 학생 + 같은 완료 고유키 두 번째 처리 실패
- 같은 완료 요청을 재시도해도 XP가 한 번만 생성
- 활동 이벤트도 한 번만 생성
- XP 생성이 실패하면 미션 완료도 함께 취소
- 이벤트 생성이 실패하면 미션·XP도 함께 취소

## 11. 활동 이벤트 중복 테스트

- 동일 학생 + 동일 `event_key` 두 번째 생성 실패
- 평가 공개 재시도로 피드백 이벤트가 중복되지 않음
- 같은 프로젝트 업데이트 재시도로 프로젝트 이벤트가 중복되지 않음
- 학생용 숨김 이벤트가 학생에게 보이지 않음
- 학부모용 숨김 이벤트가 학부모에게 보이지 않음

## 12. 프로젝트와 배지 테스트

- 진행률 -1과 101 실패
- 진행률 0과 100 성공
- 담당 선생님만 프로젝트 업데이트 작성
- 학생·학부모는 공개 업데이트만 조회
- 같은 학생에게 같은 배지 중복 지급 실패
- 같은 `award_key` 재사용 실패

## 13. 가상 seed 테스트

- 최초 실행 성공
- 두 번째 실행 성공 또는 명확한 초기화 절차 제공
- 중복 계정·학생·연결이 생기지 않음
- Auth 사용자와 `growth_users`, `growth_students` 관계 일치
- 학부모 A는 학생 A만 연결
- 선생님 A는 학생 A만 담당
- 실제 개인정보나 운영 UUID가 없음
- seed를 다시 적용하면 예측 가능한 기본 가상 상태로 복구

## 14. 개인정보와 로그 테스트

- API 오류 로그에 표시 이름 없음
- 평가 문장 원문 없음
- 이메일·전화번호 없음
- JWT, API key, 비밀번호 없음
- 요청 본문 전체 덤프 없음
- 내부 UUID와 요청 ID만으로 문제 추적 가능

## 15. 테스트 실행 계층

1. SQL 제약 테스트
2. 실제 PostgreSQL RLS 테스트
3. Supabase Auth JWT 역할별 테스트
4. API 계약 통합 테스트
5. 현재 Growth 2.0 화면 연결 테스트

RLS 검증은 `postgres`나 테이블 소유자로 실행하면 안 됩니다. 데이터 준비에만 관리 권한을 사용하고, 허용·차단 판정은 역할별 실제 `authenticated` JWT로 실행합니다.

## 16. 완료 기준

- 허용 사례 모두 성공
- 차단 사례 모두 실제 PostgreSQL 오류 또는 0행으로 차단
- skipped 테스트 없음
- 운영 URL이나 운영 키 사용 없음
- 테스트 데이터에 실제 개인정보 없음
- 새 빈 DB에서 같은 결과 재현
- 원장님이 학생·학부모·선생님 가상 화면을 직접 확인

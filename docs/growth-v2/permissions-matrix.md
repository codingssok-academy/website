# Growth 2.0 역할과 권한 설계

> RLS는 데이터베이스 장부의 각 줄 앞에 붙는 출입문입니다. 화면에서 버튼을 숨기는 것과 별개로, DB가 로그인 사용자를 다시 확인합니다.

## 1. 역할 판단 원칙

- 학생, 학부모, 선생님, 관리자는 `growth_users.role`로 판단합니다.
- 요청 본문에 `role=admin` 또는 `teacher_id=...`를 넣어도 믿지 않습니다.
- 실제 로그인 ID는 Supabase Auth의 `auth.uid()`로 확인합니다.
- 역할과 활성 상태는 DB에서 다시 조회합니다.
- 로그인하지 않은 `anon` 역할은 Growth 2.0 자료를 하나도 읽거나 쓰지 못합니다.
- `service_role`은 브라우저에 절대 넣지 않고 안전한 서버 작업에서만 사용합니다.

## 2. 역할별 기본 원칙

### 학생

- 자신의 학생 행과 성장 자료만 조회
- 자신의 XP를 직접 추가·수정하지 못함
- 미션 완료는 안전한 서버 요청을 통해서만 처리
- 선생님 평가는 `published`만 조회
- 학생 화면에는 잘한 점과 다음 목표 중심으로 표시

후보 표에는 평가 한 건의 세 문장을 함께 보관합니다. 학생에게 보완할 점을 숨기기로 결정하면 학생 홈 API는 해당 필드를 반환하지 않습니다. 운영 전 “DB 열 자체도 학생에게 감출 필요가 있다”는 결정이 나면, 학생 전용 RPC 또는 읽기 모델을 추가하고 기본 평가 표의 직접 Data API 조회 권한을 제거합니다. 이 결정은 `owner-decisions.md` 2번 승인 후 확정합니다.

### 학부모

- 활성 연결 관계의 자녀만 조회
- 다른 학생 자료는 결과가 없는 것처럼 처리
- 평가, XP, 미션, 프로젝트 기록을 직접 수정하지 못함
- `draft`와 과거 보관본을 조회하지 못함

### 선생님

- 활성 담당 관계의 학생만 조회
- 담당 학생의 평가 초안을 작성·수정
- 미담당 학생 ID를 요청에 넣어도 DB에서 차단
- 공개본을 직접 덮어쓰지 않고 새 버전을 작성

### 관리자

- 전체 연결 관계와 활성 상태 관리
- 전체 조회와 공개 평가 관리
- XP 거래를 화면에서 임의 삽입하는 대신 안전한 서버 절차 사용
- 관리자 여부는 DB 계정 역할로 확인

### 안전한 서버 작업

- 미션 완료, XP 지급, 활동 이벤트 생성을 한 거래로 처리
- 고유 요청 키로 중복 요청 차단
- 공개 처리와 이전 버전 보관
- 브라우저에 서버 비밀키를 노출하지 않음

## 4. 본인과 연결 관계 확인 방식

### 학생 본인

`growth_students.user_id = auth.uid()`인지 확인합니다.

### 학부모와 자녀

다음을 모두 만족해야 합니다.

1. `growth_parent_student_links.parent_user_id = auth.uid()`
2. 요청 학생 ID가 연결 행의 `student_id`와 같음
3. `is_active = true`
4. 종료일이 없거나 현재 날짜 이후

### 선생님과 담당 학생

다음을 모두 만족해야 합니다.

1. `growth_teacher_student_assignments.teacher_user_id = auth.uid()`
2. 요청 학생 ID가 배정 행의 `student_id`와 같음
3. `is_active = true`
4. 배정 시작일 이후이며 종료일 전

클라이언트가 보내는 `teacher_id`는 권한 판단에 사용하지 않습니다.

### 관리자

`growth_users.id = auth.uid()`, `role = 'admin'`, `is_active = true`를 DB에서 확인합니다. 사용자가 수정할 수 있는 프로필 정보나 요청 본문의 역할 문자열은 사용하지 않습니다.

## 5. 중요한 차단 방식

### XP 직접 조작 차단

- `authenticated` 역할에는 XP INSERT·UPDATE·DELETE 권한을 주지 않음
- 안전한 서버 작업만 INSERT
- `idempotency_key`와 원인 조합 고유 제약으로 중복 차단
- XP는 양수만 허용

### 미션 중복 완료 차단

- 같은 학생·미션·배정키는 한 행만 허용
- 완료 시 `completion_idempotency_key` 필수
- 같은 학생의 같은 완료 키는 한 번만 허용
- 미션 완료, XP, 이벤트를 하나의 DB 거래로 처리

### 공개 전 평가 차단

- 학생·학부모 SELECT 정책에 `status = 'published'` 조건
- 선생님은 담당 학생의 `draft` 조회·수정 가능
- 공개본은 직접 덮어쓰지 못하고 새 버전 사용

## 6. RLS 정책 의도

RLS는 “화면에 버튼이 없으니 안전하다”는 가정을 하지 않습니다.

- 학생이 주소의 학생 ID를 바꿔도 다른 학생 행이 반환되지 않음
- 학부모가 다른 자녀 UUID를 알아도 연결이 없으면 조회되지 않음
- 선생님이 미담당 학생 UUID를 넣어도 평가를 쓸 수 없음
- 요청에 `role=admin`을 넣어도 DB 계정이 관리자가 아니면 권한 없음
- 서버 비밀키는 브라우저에 없으므로 사용자가 XP 지급 경로를 흉내 낼 수 없음

## 7. 실제 DB RLS 테스트 시나리오

1. 학생 A 토큰으로 학생 A와 학생 B 조회
2. 학부모 A 토큰으로 연결 자녀와 미연결 학생 조회
3. 비활성 학부모 연결로 이전 자녀 조회
4. 선생님 A 토큰으로 담당·미담당 학생 평가 조회
5. 선생님 A가 미담당 학생 초안 INSERT 시도
6. 학생·학부모가 XP INSERT 시도
7. 학생·학부모가 `draft` 평가 SELECT 시도
8. JWT 요청 데이터에 가짜 관리자 문자열을 넣고 전체 조회 시도
9. 서비스 역할이 아닌 실제 `authenticated` 토큰으로 허용·차단 양쪽 확인
10. 모든 테스트 후 다른 테스트 데이터에 영향이 없는지 확인

RLS 테스트는 관리자나 `service_role`만 사용하면 의미가 없습니다. 학생, 학부모, 선생님, 관리자의 실제 JWT 문맥을 각각 사용해야 합니다.

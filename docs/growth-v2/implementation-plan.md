# Growth 2.0 테스트 백엔드 단계별 구현 계획

> 한 번에 한 단계만 진행합니다. 각 단계가 통과하고 원장님이 확인한 뒤 다음 단계로 갑니다.

## 공통 안전 원칙

- 운영 Supabase와 운영 DB에 연결하지 않음
- Growth 2.0 전용 독립 폴더·migration만 사용
- 가상 계정과 가상 데이터만 사용
- 실패하면 해당 단계의 독립 테스트 공간을 지우고 이전 단계에서 다시 시작
- 기존 코딩쏙 사이트와 기존 migration을 수정하지 않음

## 1단계: 독립 로컬 Supabase 프로젝트 생성

**작업 목표**

- Growth 2.0만 사용하는 빈 로컬 Supabase 공간 준비
- 기존 migration과 물리적으로 분리된 디렉터리 구성

**완료 기준**

- `localhost` 로컬 스택 시작
- 빈 DB 확인
- 운영 프로젝트 참조와 링크가 없음
- migration 번호가 `0001`부터 시작할 준비 완료

**위험 요소**

- 잘못된 작업 폴더에서 Supabase 명령 실행
- 운영 프로젝트와 실수로 link

**원장님 확인 화면**

- “Growth 2.0 전용 테스트 공간”이라는 이름과 가상 환경 안내

**되돌리는 방법**

- 로컬 스택 중지 후 Growth 2.0 전용 테스트 폴더만 삭제
- 운영 시스템에는 변화가 없으므로 별도 복구 불필요

## 2단계: 첫 migration과 가상 seed 적용

**작업 목표**

- 검토된 후보 SQL을 실제 `0001` migration으로 옮김
- 가상 학생·학부모·선생님·관리자 seed 작성

**완료 기준**

- 새 빈 DB에 migration 성공
- seed 최초·재실행 성공
- 중복 데이터 없음
- 실제 개인정보 없음

**위험 요소**

- 후보 SQL의 타입·제약 오류
- seed가 반복 실행에 안전하지 않음

**원장님 확인 화면**

- 가상 학생 2명과 연결 관계 목록

**되돌리는 방법**

- 로컬 DB reset
- migration·seed 파일의 해당 단계 커밋만 되돌림

## 3단계: 역할별 가상 Auth 계정 생성

**작업 목표**

- 학생·학부모·선생님·관리자 역할별 로그인 문맥 준비

**완료 기준**

- 가상 이메일 계정만 존재
- `auth.users`와 `growth_users` 관계 일치
- 역할과 활성 상태가 정확함

**위험 요소**

- 역할 문자열을 사용자 메타데이터만으로 판단
- 이메일 발송 또는 실제 계정 혼입

**원장님 확인 화면**

- 역할별 가상 계정 이름과 누구와 연결됐는지 표시한 표

**되돌리는 방법**

- 로컬 Auth 데이터 reset 후 seed 재실행

## 4단계: RLS와 중복 방지 실제 DB 테스트

**작업 목표**

- 학생·학부모·선생님·관리자 출입문 검증
- XP·미션·이벤트 중복 방지 검증

**완료 기준**

- `backend-test-plan.md`의 허용·차단 사례 통과
- 역할별 JWT로 실행
- skipped 테스트 없음

**위험 요소**

- `service_role`로만 검사해 실제 RLS를 우회
- RLS를 느슨하게 해서 테스트를 억지로 통과

**원장님 확인 화면**

- “학부모 A는 학생 A만 보임”, “선생님 A는 학생 A만 수정 가능” 결과표

**되돌리는 방법**

- 실패한 정책만 후보 설계로 되돌리고 로컬 DB reset
- 권한을 임시로 넓히지 않음

## 5단계: 읽기 전용 API 구현

**작업 목표**

- 학생 홈, 학부모 리포트, 선생님 담당 목록을 읽기만 연결

**완료 기준**

- 역할별 허용 데이터만 응답
- 화면 변경 없이 가상 API 응답 비교 테스트 통과
- 로그에 개인정보 없음

**위험 요소**

- 화면이 요청한 학생 ID를 그대로 신뢰
- 너무 많은 DB 열을 응답

**원장님 확인 화면**

- 현재 미리보기와 같은 내용이 API에서 읽혀 표시되는 비교 화면

**되돌리는 방법**

- UI는 기존 mock repository로 되돌림
- 읽기 API 커밋만 되돌림

## 6단계: 선생님 평가 초안 저장 API 구현

**작업 목표**

- 선생님 입력을 `draft`로 저장
- 학생·학부모에게는 아직 보이지 않게 유지

**완료 기준**

- 담당 학생 초안 저장 성공
- 미담당 학생 저장 실패
- 새로고침 후 선생님 초안 복구
- 학생·학부모 화면에는 미반영

**위험 요소**

- 초안이 즉시 공개됨
- 동시 수정으로 내용 덮어쓰기

**원장님 확인 화면**

- 선생님 화면의 “초안 저장됨”과 학생·학부모 화면 미반영 비교

**되돌리는 방법**

- 저장 API 연결을 끄고 React 임시 상태로 복귀
- DB 초안 행은 테스트 공간 reset으로 제거

## 7단계: 공개 흐름 구현

**작업 목표**

- 공개 버튼으로만 학생·학부모에게 반영
- 이전 공개본 버전 보관

**완료 기준**

- 초안 미노출
- 공개 후 두 화면 반영
- 수정 후 버전 증가와 과거 버전 보관
- 공개 재시도 중복 없음

**위험 요소**

- 원장 승인 여부가 정해지기 전 잘못된 공개 권한 구현
- 공개본 직접 수정

**원장님 확인 화면**

- 공개 전·후 세 화면 비교와 버전 기록

**되돌리는 방법**

- 공개 API 기능 플래그 비활성
- 마지막 공개본을 보관 처리하고 이전 공개본 복구

## 8단계: 현재 Growth 2.0 UI를 테스트 API에 연결

**작업 목표**

- 세 미리보기 화면의 mock 데이터를 독립 테스트 API로 교체

**완료 기준**

- 기존 디자인 유지
- 로딩·오류·빈 상태 추가
- PC·모바일 동작
- 운영 API 호출 없음

**위험 요소**

- 기존 미리보기 기능과 디자인 손상
- 테스트·운영 환경 주소 혼동

**원장님 확인 화면**

- 학생·학부모·선생님 세 화면 전체 흐름

**되돌리는 방법**

- API repository를 mock repository로 전환
- UI 코드 전체를 되돌리지 않고 데이터 연결만 교체

## 9단계: 원장님 승인 테스트

**작업 목표**

- 실제 학원 운영 순서와 문구가 자연스러운지 확인

**완료 기준**

- 평가 작성 시간이 목표 안에 들어옴
- 공개 주체와 수정 기간 결정
- 학생·학부모에게 보여 줄 문장 범위 승인
- 발견된 문제 목록과 우선순위 확정

**위험 요소**

- 기술 테스트만 통과하고 실제 수업 흐름은 불편함
- 테스트 데이터를 실제 학생 자료로 착각

**원장님 확인 화면**

- 수업 종료 → 초안 → 공개 → 학생·학부모 확인 전체 체험

**되돌리는 방법**

- 독립 테스트 환경이므로 기능을 끄고 기존 미리보기로 복귀

## 10단계: 운영 시스템 연결 가능성 별도 검토

**작업 목표**

- 운영 DB 구조와 Growth 2.0 구조의 차이 분석
- 실제 연결 여부를 결정하기 위한 별도 계획 수립

**완료 기준**

- 운영 schema-only 자료 검토
- ID 연결·개인정보·백업·이관 계획 작성
- 운영 적용 전 별도 승인

**위험 요소**

- 테스트 설계를 운영 DB에 그대로 적용
- 기존 학생·계정과 중복 생성

**원장님 확인 화면**

- 운영 영향 범위와 되돌리기 계획 요약

**되돌리는 방법**

- 검토 단계에서는 운영 변경을 하지 않음
- 승인되지 않으면 독립 테스트 프로젝트만 유지

# 코딩쏙 새 DB 전환 전용 SQL

이 폴더는 기존 운영 DB의 오래된 SQL과 분리된 **새 Supabase 전용 기준 구조**입니다.

## 안전 원칙

- 기존 운영 DB와 현재 staging DB에는 자동으로 적용하지 않습니다.
- 실제 학생·학부모·관리자 정보나 고정 비밀번호를 SQL에 넣지 않습니다.
- 각 단계는 빈 시험 DB에서 검증한 뒤 순서대로 적용합니다.
- 기존 `supabase/migrations` 및 `supabase/*.sql` 파일은 수정하지 않습니다.
- 운영 전환 전까지 Vercel 환경변수와 운영 도메인은 변경하지 않습니다.

## 1단계: 계정과 연결 관계

`001_identity_access.sql`은 다음 항목만 만듭니다.

1. 로그인 계정의 역할과 상태를 보관하는 `profiles`
2. 학원 학생 명부인 `students`
3. 학부모 계정과 자녀를 연결하는 `parent_student_links`
4. 선생님 계정과 담당 학생을 연결하는 `teacher_student_assignments`
5. 학생 로그인 번호와 학부모 인증번호를 원문이 아닌 해시로 보관하는 비공개 저장소
6. 학생 본인·연결된 학부모·담당 선생님·관리자를 구분하는 RLS 권한

학부모가 별도 계정을 만들지 않는 현재 방식도 지원할 수 있도록, 서버만 호출할 수 있는 인증번호 확인 함수를 함께 둡니다. 인증번호 원문은 DB 표에 저장하지 않습니다.

## 2단계: 관리자 인증번호 관리

`002_access_code_admin.sql`은 관리자가 인증번호의 발급 여부만 확인하고, 인증번호를 안전하게 해제할 수 있는 서버 전용 함수를 추가합니다. 원문 번호를 다시 읽는 함수는 만들지 않습니다.

## 3단계: Growth 2.0 성장기록

`003_growth_records.sql`은 월 단위 성장기록을 저장하는 기준 표를 만듭니다. 선생님이 작성하는 배운 개념, 잘한 점, 보완할 점, 다음 목표와 학부모 메시지를 담고, `공개 완료` 상태의 기록만 학생과 연결된 학부모가 볼 수 있습니다.

선생님 내부 메모는 별도의 비공개 표에 보관하여 학생·학부모 화면에서 실수로 조회할 수 없게 합니다. 이 단계에도 실제 학생 자료나 초기 데이터는 포함하지 않습니다.

`verify_003_growth_records.sql`은 새 서울 시험 DB에서 학생·학부모·담당 선생님·미담당 선생님·관리자·비로그인 역할을 가짜 자료로 검사합니다. 모든 자료는 하나의 트랜잭션 안에서 만든 뒤 `rollback`하여 남기지 않습니다.

## 4단계: 월별 출석

`004_monthly_attendance.sql`은 수업일별 `예정·출석·결석·보강 완료` 기록을 저장하고 달력의 월 단위로 합산합니다. 학생과 연결된 학부모는 해당 학생의 출석만 볼 수 있고, 담당 선생님과 관리자만 기록을 작성하거나 수정할 수 있습니다.

출석 메모는 학부모에게 보여도 되는 짧은 안내만 저장합니다. 선생님 내부 관찰 내용은 출석 메모에 넣지 않도록 DB 설명에도 명확히 표시했습니다. 기존 Growth 2.0 화면과 연결하기 위한 월별 조회 함수와 선생님 저장 함수도 같은 이름으로 제공합니다.

`verify_004_monthly_attendance.sql`은 월별 합계와 학생·학부모·담당 선생님·미담당 선생님·관리자·서버·비로그인 권한을 가짜 자료로 검사합니다. 검사용 자료는 실행 마지막에 모두 `rollback`합니다.

`005_fix_attendance_returning_permissions.sql`은 선생님 저장 함수가 숨겨진 작성자 ID까지 다시 읽으려던 문제를 보정합니다. 이미 적용된 `004`는 변경하지 않고, 화면에 필요한 안전한 출석 필드만 반환하도록 함수를 교체합니다.

## 5단계: 전체 메시지(공지)

`006_announcements.sql`은 관리자가 학원 전체에 보내는 공지를 저장합니다. 현재 홈페이지가 사용하는 제목, 내용, 상단 고정 기능과 바로 연결되며, 관리자가 `공개 완료`한 메시지만 승인된 학생·학부모·선생님 계정에 보입니다.

작성 중이거나 보관한 메시지는 관리자만 볼 수 있습니다. 작성한 관리자 계정 ID는 감사용으로 DB에 보관하지만 학생·학부모 화면에는 전달하지 않으며, 새 공지가 즉시 나타나도록 Supabase Realtime 연결도 함께 준비합니다. 이 단계에도 실제 공지나 개인정보는 넣지 않습니다.

`verify_006_announcements.sql`은 공개·작성 중·보관 메시지를 만든 뒤 학생·학부모·선생님·승인 대기 계정·관리자·서버·비로그인 역할의 읽기와 쓰기 권한을 확인합니다. 검사용 가짜 계정과 공지는 마지막에 모두 `rollback`합니다.

## 6단계: 학습 진행·XP·레벨

`007_learning_progress_xp.sql`은 모든 학생이 `XP 0·레벨 1`에서 시작하도록 하고, 코스별 완료 화면과 완료율을 저장합니다. 학생이 학습할 때 받는 XP는 화면에서 임의의 숫자를 저장하지 않고, DB 함수가 활동 종류별 고정 점수를 계산하여 중복 없이 누적합니다. 레벨도 누적 XP로 자동 계산되므로 학부모 화면과 학생 화면의 숫자가 서로 달라지지 않습니다.

학생은 자기 코스 진행 기록만 저장할 수 있습니다. 학생 본인·연결된 학부모·담당 선생님·관리자만 허용된 학생의 XP와 학습 진행을 읽을 수 있으며, 비로그인 사용자는 접근할 수 없습니다. 기존 홈페이지의 XP API는 새 DB 전환 전에 이 안전한 함수로 연결하는 별도 단계가 필요합니다.

`verify_007_learning_progress_xp.sql`은 레벨 1 시작, XP 자동 계산과 중복 차단, 코드 실행 하루 보상 한도, 코스 완료 저장, 학생·학부모·담당/미담당 선생님·승인 대기 계정·관리자·서버·비로그인 권한을 가짜 자료로 확인합니다. 모든 검증 자료는 실행 마지막에 `rollback`합니다.

홈페이지의 `/api/xp`는 새 DB 전환 시 `growth_api_award_xp`만 호출하도록 연결했습니다. 웹 서버는 로그인과 요청 횟수를 확인하고, 실제 점수 계산·중복 확인·저장·레벨 계산은 검증된 DB 함수가 한 번에 처리합니다. 새 시험 환경 연결 전에는 운영 홈페이지 동작이 바뀌지 않습니다.

## 7단계: 최근 학습 활동·학습시간

`008_student_activity_log.sql`은 학생이 어느 코스·단원·학습 화면을 방문했는지와 머문 시간을 저장합니다. 기존의 `지난 학습 이어하기`, 학부모 현황판의 최근 학습 활동, 관리자 학습 현황이 같은 기록을 사용할 수 있도록 현재 홈페이지의 필드 이름을 유지합니다.

학생 이름과 방문 시작 시각은 브라우저에서 받은 값을 그대로 저장하지 않고 DB가 로그인된 활성 학생 명부를 기준으로 다시 넣습니다. 종료 시각과 학습시간도 DB가 계산하고 하루를 넘지 않도록 제한합니다. 학생 본인·연결된 학부모·담당 선생님·관리자만 허용된 학생의 기록을 읽을 수 있고, 비로그인 사용자는 접근할 수 없습니다. 이 단계에도 실제 학습 기록이나 개인정보는 넣지 않습니다.

`verify_008_student_activity_log.sql`은 학생 본인 저장, 다른 학생 기록 위조 차단, 학생 이름·학습시간 DB 계산, 연결 학부모·담당/미담당 선생님·승인 대기 계정·관리자·서버·비로그인 권한을 가짜 자료로 확인합니다. 모든 검증 자료는 실행 마지막에 `rollback`합니다.

## 8단계: 학생 결과물 파일

`009_student_files.sql`은 엔트리·스크래치·문서·이미지 등 학생 결과물의 정보를 저장하고, 실제 파일은 50MB 제한이 적용된 비공개 `student-files` 저장소에 보관합니다. 파일 경로에는 학생 ID와 올린 사람의 역할을 포함하며, DB가 실제 활성 학생·승인된 업로더 관계를 다시 확인하므로 브라우저가 다른 학생이나 선생님 이름으로 위조할 수 없습니다.

학생과 연결 학부모에게 보여도 되는 파일과 선생님·관리자만 보는 내부 파일을 구분합니다. 학생 본인·연결 학부모·담당 선생님·관리자만 허용된 파일을 읽을 수 있고, 저장·수정·삭제는 로그인 검사를 거친 홈페이지 서버만 수행합니다. 비공개 내부 경로는 일반 화면에 제공하지 않으며 이 단계에도 실제 파일이나 개인정보를 넣지 않습니다.

`verify_009_student_files.sql`은 실제 파일 업로드 없이 비공개 저장소 설정, 학생·학부모 공개 파일과 선생님 전용 파일의 분리, 담당/미담당 선생님·관리자·승인 대기 계정·서버·비로그인 권한, 파일정보 위조와 직접 변경 차단을 검사합니다. 가짜 계정과 파일정보는 마지막에 모두 `rollback`합니다.

홈페이지의 학생 파일 API는 새 DB 모드에서 DB 권한 함수를 다시 확인한 뒤에만 1분짜리 다운로드 주소를 만듭니다. 연결된 학부모는 공개된 자녀 파일만 받을 수 있고, 담당하지 않은 선생님은 파일 목록과 다운로드 주소에 모두 접근할 수 없습니다. 현재 운영 방식은 새 DB 모드를 켜기 전까지 그대로 유지됩니다.

로컬 홈페이지를 이 fresh-test 프로젝트에 연결한 뒤 `node scripts/fresh-student-files-live-check.mjs`를 실행하면 학생 회원가입·로그인·파일 업로드·학부모 다운로드·학부모 삭제 차단·미담당 선생님 차단·담당 선생님 허용을 실제 API와 저장소로 연속 검사합니다. 스크립트는 지정된 fresh-test DB와 로컬 주소가 아니면 즉시 중단하며, 검사에 사용한 가짜 학생·선생님·파일은 성공 여부와 관계없이 마지막에 정리합니다.

## 9단계: 학생·선생님 1:1 메시지

`010_direct_messages.sql`은 학생이 담당 선생님 또는 관리자에게 질문을 남기고 답변을 받을 수 있는 비공개 1:1 메시지 표를 만듭니다. 학생과 담당 선생님은 자신이 참여한 대화만 읽을 수 있고, 관리자는 학원 운영을 위해 전체 학생 대화를 확인할 수 있습니다. 학부모·승인 대기 계정·미담당 선생님·비로그인 사용자는 메시지를 읽거나 보낼 수 없습니다.

보내는 사람 ID와 이름, 학생 연결 ID, 읽음 시간은 브라우저 값을 믿지 않고 DB가 로그인 계정과 학원 명부를 기준으로 다시 정합니다. 메시지 본문은 2,000자로 제한하고, 이미 보낸 내용과 참여자는 수정하거나 삭제할 수 없습니다. 수신자만 읽음 처리할 수 있으며, 실시간 새 메시지 표시를 위한 Realtime 연결도 준비합니다. 이 단계에는 실제 대화나 개인정보를 넣지 않습니다.

## 이후 연결 작업

이 SQL은 안전한 DB 뼈대입니다. 학생 로그인·회원가입과 학부모 세션, 관리자 인증번호 발급·재발급에는 서버 전용 해시 인증 어댑터가 준비되어 있습니다. 새 테스트 DB에서 전체 연결 검증을 마치기 전에는 운영 홈페이지에 연결하지 않습니다.

새 인증 경로를 시험할 때는 서버 환경변수 `SUPABASE_ACCESS_CODE_MODE=hashed`를 사용합니다. 이 값은 새 DB가 준비된 시험 환경에서만 설정하며, 현재 운영 환경에는 아직 설정하지 않습니다.
